arc-units

Arc shows you one balance two different ways.
Confuse them and you are wrong by a trillion.

arc-units.vercel.app github.com/JspIIV/arc-units

The problem

USDC is Arc's native gas token. That means one balance is exposed through two interfaces at different scales.

nativeERC-20
read viagetBalance()balanceOf()
decimals186
address—0x3600…0000
truncatesnoyes

They are not two tokens. A precompile forwards ERC-20 calls to the native balance — so a UI that shows both is double-counting the same money.

Nobody agrees which is which

While building, I found public sources stating the native token is 6-decimal. Anyone who believes that is off by a factor of 1012.

So I stopped reading and measured it. Both interfaces, same account, pinned to one block:

8/8 accounts satisfy erc20 === floor(native / 1e12)
8/8 accounts hold sub-6-decimal dust invisible to the ERC-20 view

CONFIRMED: native is 18-decimal, the ERC-20 view is a
           truncating 6-decimal projection

Reproducible: npm run probe derives this from live testnet, from scratch.

Consequence 1 — gas disappears

Gas on Arc runs around 0.000000025 USDC per unit.

read as native (18d)

0.000483 USDC

a plain transfer, correctly priced

read as ERC-20 (6d)

0

three orders of magnitude below what it can represent

Any fee estimate that goes through the token interface silently rounds to nothing.

Consequence 2 — dust gets stranded

"Send my whole balance" over ERC-20 can never move everything. Every account I sampled was already carrying value no token transfer can reach. 

native : 4985632220860000000   (4.98563222086 USDC)
erc20  : 4985632               (4.985632   USDC)
dust   :          220860000000 (0.00000022086 USDC — unreachable)

Small per account. Not small across a payments chain built for institutions.

The fix: make it a compile error

Both interfaces are plain bigint, so nothing stops you adding a gas price to a token amount. arc-units gives each one its own type. 

const balance = native(1_234_567_890_123_456_789n);  // getBalance()

const { value, dust } = toErc20(balance);
// value: 1234567n        what the recipient actually sees
// dust:  890123456789n   what stays behind

toErc20Exact(balance);  // throws rather than lose it

balance + erc20Amount   // ✗ compile error

Converting down returns the dust alongside the value, so callers have to decide what happens to it. Silence is not an option the API offers.

On-chain: DustLens

The same invariant, checkable from inside the EVM.

networkArc Testnet (5042002)
statusverified — full bytecode match

inspect(address) returns the native balance, the ERC-20 balance, the dust between them, and whether they agree — in a single call, which also closes the torn-read window that separate eth_calls have across Arc's ~500 ms blocks.

splitEvenly(address[]) distributes native value exactly and hands the remainder to the first recipient. Verified on-chain: the contract keeps 0.
